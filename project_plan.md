# Raw Performance Lab

## Project Overview

Raw Performance Lab is a student portal API built to practice backend engineering with Express.js, TypeScript, PostgreSQL, Prisma, and Docker.

The project has two main objectives:

1. Build a functional, secure student portal API with authentication, course management, and course registration.
2. Use the completed API as a performance case study to measure, identify, and improve database efficiency, API throughput, response times, security, and reliability.

The goal is not simply to make the API work. It is to understand how it behaves under load, identify bottlenecks using evidence, and document measurable improvements.

## Technology Stack

- **Runtime:** Node.js
- **Language:** TypeScript
- **Framework:** Express.js 5
- **Database:** PostgreSQL
- **ORM:** Prisma 7
- **Database driver:** `pg` with `@prisma/adapter-pg`
- **Validation:** Zod
- **Authentication:** JWT
- **Password hashing:** Argon2id or bcrypt
- **Logging:** Pino and pino-http
- **Security:** Helmet, CORS configuration, rate limiting
- **Testing:** Vitest and Supertest
- **Load testing:** Autocannon
- **Containerization:** Docker and Docker Compose
- **CI:** GitHub Actions

Redis will not be introduced initially. It will only be considered if measurements show a specific problem that caching or another Redis-based solution could reasonably solve.

# Phase 1: Database Design and Setup

## 1. Student Model

Represents students registered on the platform.

| Field          | Description                                         |
| -------------- | --------------------------------------------------- |
| `id`           | UUID primary key                                    |
| `matricNumber` | Unique matriculation number generated by the server |
| `email`        | Unique email address                                |
| `passwordHash` | Securely hashed password                            |
| `role`         | Defaults to `STUDENT`                               |
| `createdAt`    | Account creation timestamp                          |
| `updatedAt`    | Last update timestamp                               |

### Requirements

- Email addresses must be unique.
- Matriculation numbers must be unique.
- Passwords must never be stored in plaintext.
- Matriculation numbers must be generated by the server.
- Students must not be allowed to assign their own roles.

## 2. Course Model

Represents courses available for registration.

| Field        | Description                       |
| ------------ | --------------------------------- |
| `id`         | UUID primary key                  |
| `courseCode` | Unique course code, e.g. `CHM101` |
| `courseName` | Course title                      |
| `isActive`   | Boolean, defaults to `true`       |
| `isElective` | Boolean, defaults to `false`      |
| `createdAt`  | Creation timestamp                |
| `updatedAt`  | Last update timestamp             |

### Requirements

- Course codes must be unique.
- New courses should be active by default.
- Inactive courses cannot receive new registrations.
- Deactivating a course must not automatically delete existing registrations.

## 3. CourseRegistration Model

Represents the many-to-many relationship between students and courses.

| Field          | Description                       |
| -------------- | --------------------------------- |
| `id`           | UUID primary key                  |
| `studentId`    | Foreign key referencing `Student` |
| `courseId`     | Foreign key referencing `Course`  |
| `registeredAt` | Registration timestamp            |

### Requirements

- A student can register for multiple courses.
- A course can have multiple registered students.
- A student cannot register for the same course twice.
- Enforce a unique composite constraint on `(studentId, courseId)`.
- Use foreign keys to preserve referential integrity.
- Use transactions for operations that must succeed or fail together.

## 4. Admin Model

Represents administrators who manage the student portal.

| Field          | Description                     |
| -------------- | ------------------------------- |
| `id`           | UUID primary key                |
| `name`         | Unique administrator login name |
| `passwordHash` | Securely hashed password        |
| `role`         | `ADMIN`                         |
| `createdAt`    | Account creation timestamp      |
| `updatedAt`    | Last update timestamp           |

### Requirements

- Create the initial admin account through a seed script.
- Read initial credentials from environment variables.
- Hash the password before storing it.
- Never hardcode production credentials in the source code.
- Restrict administrative endpoints to authenticated administrators.

# Phase 2: API Implementation

All endpoints use the `/api/v1` prefix.

## 1. Authentication Endpoints

### Student Registration

`POST /api/v1/students/register`

Access: Public.

Request body:

```json
{
  "email": "student@example.com",
  "password": "a-strong-password"
}
```

Requirements:

- Validate the request using Zod.
- Normalize email addresses consistently.
- Reject duplicate email addresses.
- Hash passwords before storing them.
- Generate a unique matriculation number.
- Assign the `STUDENT` role on the server.
- Return an appropriate success response without exposing the password hash.

### Student Login

`POST /api/v1/students/login`

Access: Public.

Request body:

```json
{
  "email": "student@example.com",
  "password": "a-strong-password"
}
```

Requirements:

- Validate the request body.
- Verify the password against the stored hash.
- Return a JWT after successful authentication.
- Return a generic authentication error for invalid credentials.
- Never return password hashes.

### Admin Login

`POST /api/v1/admin/login`

Access: Public.

Request body:

```json
{
  "name": "Admin",
  "password": "admin-password"
}
```

Requirements:

- Verify administrator credentials.
- Issue a JWT containing the administrator's identity and role.
- Do not expose administrator credentials or password hashes.
- Apply appropriate login rate limiting.

## 2. Admin Endpoints

All endpoints below require an authenticated administrator.

| Method  | Endpoint                           | Purpose                         |
| ------- | ---------------------------------- | ------------------------------- |
| `GET`   | `/api/v1/admin/students`           | List students                   |
| `GET`   | `/api/v1/admin/students/:id`       | Get a student by ID             |
| `POST`  | `/api/v1/admin/courses`            | Create a course                 |
| `GET`   | `/api/v1/admin/courses`            | List all courses                |
| `PATCH` | `/api/v1/admin/courses/:id`        | Update course details           |
| `PATCH` | `/api/v1/admin/courses/:id/status` | Activate or deactivate a course |

### Create Course

`POST /api/v1/admin/courses`

Request body:

```json
{
  "courseCode": "CHM101",
  "courseName": "General Chemistry",
  "isActive": true,
  "isElective": false
}
```

Requirements:

- Validate input with Zod.
- Require a unique course code.
- Default `isActive` to `true` when omitted.
- Default `isElective` to `false` when omitted.
- Return appropriate errors for duplicate course codes and invalid data.

### List Students

`GET /api/v1/admin/students`

Requirements:

- Require administrator authentication and authorization.
- Support pagination.
- Return only necessary student fields.
- Never expose password hashes.
- Use consistent response and error formats.

## 3. Student Endpoints

All student-specific endpoints require student authentication unless otherwise stated.

### Browse Courses

`GET /api/v1/courses`

Requirements:

- Return active courses by default.
- Support pagination when the dataset becomes large.
- Validate query parameters.
- Do not expose unnecessary internal fields.

### Get Own Profile

`GET /api/v1/students/me`

Requirements:

- Return the authenticated student's profile.
- Derive the student ID from the verified token.
- Never trust a client-supplied student ID to identify the current user.

### Get Registered Courses

`GET /api/v1/students/me/courses`

Requirements:

- Return the authenticated student's registered courses.
- Include relevant course information.
- Use efficient database queries.
- Avoid unnecessary repeated database queries.

### Register for Courses

`POST /api/v1/students/me/courses`

Request body:

```json
{
  "courseIds": ["course-uuid-1", "course-uuid-2"]
}
```

Requirements:

- Validate the request body.
- Confirm that all requested courses exist.
- Confirm that all requested courses are active.
- Prevent duplicate registrations.
- Use a database transaction for the batch operation.
- Reject the entire batch if any requested course is invalid.
- Enforce duplicate prevention at the database level, not only in application code.
- Return clear errors for invalid course IDs and existing registrations.

### Unregister from a Course

`DELETE /api/v1/students/me/courses/:courseId`

Requirements:

- Allow students to remove only their own registrations.
- Return an appropriate response if the registration does not exist.
- Define and enforce any course withdrawal restrictions if introduced later.

# Phase 3: Application Structure and Engineering Practices

Organize the application into modules with clear responsibilities.

Suggested structure:

```text
src/
├── app.ts
├── server.ts
├── config/
│   └── env.ts
├── lib/
│   └── prisma.ts
├── middleware/
│   ├── authenticate.ts
│   ├── authorize.ts
│   ├── error-handler.ts
│   ├── not-found.ts
│   └── validate.ts
├── modules/
│   ├── auth/
│   │   ├── auth.routes.ts
│   │   ├── auth.controller.ts
│   │   ├── auth.service.ts
│   │   └── auth.schema.ts
│   ├── students/
│   │   ├── student.routes.ts
│   │   ├── student.controller.ts
│   │   ├── student.service.ts
│   │   └── student.schema.ts
│   ├── courses/
│   │   ├── course.routes.ts
│   │   ├── course.controller.ts
│   │   ├── course.service.ts
│   │   └── course.schema.ts
│   └── registrations/
│       ├── registration.routes.ts
│       ├── registration.controller.ts
│       ├── registration.service.ts
│       └── registration.schema.ts
├── utils/
│   └── ...
└── types/
    └── ...
prisma/
├── schema.prisma
└── seed.ts
tests/
├── integration/
└── unit/
```

Adjust the structure when justified, but avoid unnecessary abstraction.

### Responsibilities

- **Routes:** Map HTTP methods and paths to middleware and controllers.
- **Controllers:** Handle HTTP requests and construct responses.
- **Services:** Implement business rules and coordinate database operations.
- **Validation:** Validate incoming request data using Zod.
- **Middleware:** Handle authentication, authorization, validation, and common request processing.
- **Prisma:** Manage database access.
- **Error handler:** Return consistent errors without leaking internal details.

### General Requirements

- Use strict TypeScript.
- Avoid `any` unless there is a documented reason.
- Keep environment variables out of source control.
- Validate environment configuration during startup.
- Use centralized error handling.
- Use structured logging with Pino.
- Do not log passwords, JWTs, API secrets, or sensitive request bodies.
- Use a consistent response format.
- Separate application creation from server startup to make testing easier.

# Phase 4: Testing and Functional Verification

Before performance optimization, establish that the API behaves correctly.

## Unit Tests

Test business logic such as:

- Student registration validation.
- Email normalization.
- Course eligibility checks.
- Duplicate registration handling.
- Authorization rules.
- Error mapping.

## Integration Tests

Test the API and database together.

Required scenarios:

- Successful student registration.
- Duplicate email rejection.
- Successful and unsuccessful login.
- Admin-only endpoint protection.
- Student access to another student's resources being rejected.
- Successful course creation.
- Duplicate course code rejection.
- Registration for active courses.
- Rejection of inactive courses.
- Duplicate course registration prevention.
- Transaction rollback when a batch registration fails.
- Pagination and validation of query parameters.

Use a dedicated test database. Tests must not accidentally modify development or production data.

## Functional Baseline

Before optimizing, record:

- Which tests pass.
- Which endpoints work.
- Existing response structures.
- Existing database constraints and indexes.
- Any known functional limitations.

This establishes the baseline against which future changes can be evaluated.

# Phase 6: Core Case Study — Security, Database Optimization, API Performance, and Reliability

**This is the most important phase of the project.** The goal is to use the working API as a controlled engineering experiment.

Do not optimize based on intuition alone. Measure the existing implementation, identify a specific bottleneck, make one targeted change at a time, and measure again.

## 1. Establish a Performance Baseline

Create a reproducible load-testing procedure using Autocannon.

Select representative endpoints:

- `GET /api/v1/courses`
- `GET /api/v1/students/me/courses`
- `GET /api/v1/admin/students`
- An authenticated registration endpoint where appropriate

Requirements:

- Seed the database with realistic test data.
- Test multiple dataset sizes, such as 1,000, 10,000, and 50,000 students where hardware permits.
- Test realistic distributions of courses and registrations.
- Run tests with documented concurrency and duration.
- Separate public and authenticated endpoint tests.
- Avoid measuring only a single request or a single run.
- Repeat runs and compare results under similar conditions.

Record:

- Requests per second.
- Median response time (p50).
- p95 response time.
- p99 response time.
- Error rate.
- CPU and memory usage where available.
- Database query count and duration for relevant operations.

Save the baseline results in a document such as `docs/performance-baseline.md`.

Do not claim an improvement unless the measurements support it.

## 2. Database Performance Optimization

Investigate database performance before introducing caching.

### Indexing

- Identify frequent lookup and filtering patterns.
- Verify indexes on unique fields such as email, matriculation number, and course code.
- Add or verify the composite unique constraint on `(studentId, courseId)`.
- Evaluate an index on `courseId` for registration lookups.
- Evaluate additional indexes only when query patterns justify them.
- Compare query plans using PostgreSQL `EXPLAIN` and, where appropriate, `EXPLAIN ANALYZE`.

### Query Optimization

- Identify slow queries.
- Avoid retrieving unnecessary columns.
- Use Prisma `select` and `include` deliberately.
- Detect and eliminate N+1 query patterns.
- Compare appropriate joins, relation queries, and separate queries.
- Use pagination for large result sets.
- Compare offset pagination with cursor pagination at larger dataset sizes.
- Avoid fetching all records into application memory.
- Evaluate batch operations where they reduce unnecessary database round trips.

### Transactions and Concurrency

- Review transaction boundaries.
- Avoid holding transactions open longer than necessary.
- Test concurrent course registrations.
- Ensure database constraints prevent duplicate registrations during races.
- Investigate lock contention and transaction timeouts.
- Ensure retries, if implemented, are limited to appropriate transient failures.

### Measurement

For each database optimization, document:

1. The original problem.
2. The baseline measurement.
3. The change made.
4. The resulting measurement.
5. Any trade-offs, such as additional index storage or slower writes.

## 3. API Performance Optimization

Investigate the application layer after measuring database behavior.

### Response Efficiency

- Return only fields clients need.
- Paginate collection endpoints.
- Avoid unnecessary serialization and transformations.
- Avoid redundant database queries.
- Measure the cost of validation, authentication, and logging where relevant.

### Concurrency and Resource Usage

- Test under increasing concurrent request counts.
- Identify CPU-bound and I/O-bound bottlenecks.
- Monitor memory usage during longer tests.
- Check for unbounded arrays, repeated queries, and resource leaks.
- Investigate connection pool configuration and database connection pressure.
- Configure sensible request limits and timeouts.
- Avoid adding worker threads or other concurrency mechanisms without evidence that they are needed.

### Caching Experiment

Only consider caching after identifying a workload that benefits from it.

If measurements justify it:

- Identify suitable read-heavy data.
- Define cache keys and expiration.
- Define invalidation behavior when course information changes.
- Avoid caching sensitive user-specific data without an explicit security design.
- Compare latency and throughput with and without caching.
- Document the additional complexity and consistency trade-offs.

Redis is optional and must be justified by the results.

## 4. Security Hardening

Review security as a separate workstream, not just a performance task.

### Authentication

- Hash passwords using Argon2id or bcrypt.
- Use strong, environment-provided JWT secrets.
- Set and verify token expiration.
- Validate JWT signature, issuer, audience, and other relevant claims when configured.
- Return generic login errors.
- Rate-limit login and registration endpoints.
- Ensure authentication failures do not expose internal details.

### Authorization

- Enforce role-based access control for admin routes.
- Verify that students can access only their own records.
- Never trust a role or user ID supplied in a request body.
- Derive the authenticated identity from the verified token.
- Test privilege escalation and unauthorized access scenarios.

### Input and HTTP Security

- Validate request bodies, parameters, and query strings with Zod.
- Enforce reasonable request body size limits.
- Configure CORS for explicitly allowed origins.
- Use Helmet with an appropriate configuration.
- Prevent mass assignment by accepting only explicitly allowed fields.
- Use Prisma safely and avoid unsafe raw SQL construction.
- Return consistent error responses without leaking stack traces or database internals.
- Avoid logging passwords, tokens, and sensitive personal information.

### Abuse and Resource Protection

- Apply appropriate rate limits.
- Limit pagination sizes.
- Reject excessively large batches of course IDs.
- Set appropriate timeouts and resource limits.
- Ensure malformed or abusive requests do not cause unbounded work.

### Security Verification

Write automated tests for:

- Missing and invalid tokens.
- Expired tokens.
- Student access to admin endpoints.
- Unauthorized access to other students' records.
- Mass-assignment attempts.
- Invalid and oversized inputs.
- Login rate limiting.
- Duplicate registration attempts under concurrency.

Use dependency audits and document the findings. A passing test suite does not by itself prove the application is secure.

## 5. Reliability and Error Handling

Test behavior when dependencies or requests fail.

Requirements:

- Use a centralized error handler.
- Return suitable HTTP status codes.
- Distinguish validation, authentication, authorization, conflict, and unexpected server errors.
- Avoid exposing internal exceptions to clients.
- Log unexpected errors with request context while redacting secrets.
- Handle database connection failures gracefully.
- Test transaction rollback.
- Verify that repeated requests do not create duplicate records.
- Ensure the server starts only when required configuration is valid.
- Add a lightweight health endpoint.
- Add a readiness check that verifies required dependencies when appropriate.

Keep health and readiness endpoints inexpensive. Do not make them perform heavy database operations on every request.

## 6. Regression and Comparative Testing

After each optimization or security change:

- Run the full test suite.
- Repeat the same load-test scenarios used for the baseline.
- Keep test duration, concurrency, dataset, and environment as consistent as possible.
- Compare p50, p95, p99, throughput, and error rates.
- Check whether an improvement in one endpoint causes regressions elsewhere.
- Record changes that did not improve performance as well as those that did.

Do not combine multiple major optimizations into a single experiment. Isolate changes so the results are interpretable.

## 7. Final Case Study Report

Create `docs/performance-report.md`.

Include:

- System architecture and environment.
- Database schema and important indexes.
- Dataset sizes and workload scenarios.
- Baseline measurements.
- Identified bottlenecks and supporting evidence.
- Changes implemented.
- Before-and-after measurements.
- Security issues found and resolved.
- Reliability improvements.
- Failed experiments and lessons learned.
- Known limitations.
- Remaining optimization opportunities.

Use tables and charts where helpful.

The final report should make it possible for another developer to reproduce the tests and understand why each optimization was made.

- [ ] Course management and registration work correctly.

- [ ] The final report explains the trade-offs and remaining limitations.

## Guiding Principle

Build a correct API first. Establish a measurable baseline second. Then optimize the database, application, security, and reliability based on evidence.

The purpose of this project is not to add as many technologies as possible. It is to demonstrate that you can understand a backend system, measure its behavior, identify weaknesses, make informed changes, and explain the results.
